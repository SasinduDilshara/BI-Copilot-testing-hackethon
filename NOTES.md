# MQTT

1. In prompt-1:v1, Copilot initially did not know the live MQTT tests needed a second `Config.toml` in the `tests` directory. The first test run failed, after which it requested the configuration again in another form.
2. The prompt-1:v1 `testMalformedPayloadDoesNotProduceAlert` broker test is a false positive. The alert listener is stopped by the preceding test, and the malformed case publishes for `dev-integration-2` while checking the cleared in-memory entry for `dev-integration-1`. It cannot detect an erroneous alert for the malformed message.
3. The prompt-1:v1 live-broker setup is not reproducible from the commit alone. Both `Config.toml` files are gitignored and contain absolute local certificate paths, so a clean checkout needs undocumented local configuration before `bal test` can run.
4. Prompt-1:v1 validates `recordedAt` with a shape-only regular expression. Impossible timestamps such as `2026-99-99T99:99:99Z` match even though the generated documentation says invalid timestamps are rejected.
5. Prompt-1:v2 publishes the retained `online` health snapshot only while processing a temperature message. It does not publish at service startup, so after an unexpected shutdown and restart the retained last-will `offline` status remains visible until another temperature message arrives.
6. Prompt-1:v2 adds no broker tests for manual acknowledgement or last-will behavior. Its retained-health test does not clear the broker's retained value and can pass using stale state from a previous run.
7. The prompt-1:v3 `testUnconfiguredCargoReadingDoesNotProduceAlert` test repeats the false-positive negative-test pattern: the alert listener has stopped, the test publishes for `dev-integration-3`, and it checks only the cleared entry for `dev-integration-1`.
8. Prompt-1:v3 does not check that the device segment in `fleet/{deviceId}/commands` matches the payload's `deviceId`, so a command published to one device's topic can be accepted and answered as another device.
9. In MQTT connector 1.4.2, `caller->respond()` and `caller->complete()` enqueue independent asynchronous tasks and return before broker completion. Prompt-1:v3 calls them in source order, but the connector cannot guarantee that the response succeeds before acknowledgement; the tests do not cover this failure path.
10. Prompt-2:v1 configures the vibration subscription at QoS 1 even though the prompt requires QoS 2. Prompt-2:v3 preserves this incorrect value, and the broker tests also publish and subscribe at QoS 1, so they do not detect the mismatch.
11. Prompt-2:v2 puts MQTT `responseTopic` and `correlationData` on diagnostic requests, but the response handler ignores the response message's MQTT `correlationData` and trusts the JSON `correlationId` instead. The live response test sends no MQTT correlation property, so it does not prove MQTT request-response correlation and could accept a JSON response for the wrong pending request.
12. Prompt-2:v2 publishes a diagnostic request before registering its correlation ID as pending. A sufficiently fast response can arrive first, be discarded as unknown, and then leave the newly registered request to time out and increment the unanswered counter.
13. The MQTT tests require ignored local `Config.toml` files and a live broker, provide no tracked example configuration or broker setup, and have no test groups separating unit tests from live-broker tests. Fixed client IDs also make concurrent runs against the same broker prone to collisions.
14. Both MQTT package manifests declare Ballerina distribution 2201.13.6, but final verification ran with Ballerina 2201.13.5. The generated ignored dependency files also record 2201.13.5, so the declared distribution was not the one tested.
